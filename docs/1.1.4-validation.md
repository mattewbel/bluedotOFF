## Speed measurement before any change (2026-10-18, Fold7, USB watch path)

Build: release-signed measurement build (`artifacts/archive/1.1.4-tests/measure-baseline-b.apk`, commit with the batch
timers). Fixture: 26 disposable apps (20 single + 3 shared groups of 2, scratchpad `perf_fixture/build_perf.py`),
the owner's 213 records kept, so the journal has its real size (239 records during the test).

| Run | Wall (tap to result) | Shared groups | Journal commits | Target reads | Diagnostics | Journal reads |
|---|---|---|---|---|---|---|
| Add 26 (1st, no counters) | 9218 ms | ~5.0 s (log gap) | - | - | - | - |
| Restore 26 | 9162 ms | 3x / 4909 ms | 40x / 1765 ms | 156x / 620 ms | 306x / 11 ms | 30x / 71 ms |
| Add 26 | 9284 ms | 3x / 5041 ms | 40x / 1903 ms | 156x / 612 ms | 306x / 12 ms | 27x / 56 ms |
| Watch after updating all 26 (Android kept them hidden) | 248 / 260 ms per round of 26 | - | - | 26x / ~137 ms | - | ~25x / ~95 ms |

Findings: the 20 single apps take ~4.2 s together (waits overlapped, 12 in flight); the 3 groups (6 apps) take ~5 s,
one after another (~1.65 s each: the 0/0.5/1.5 s checks are not overlapped across groups). Journal commits are ~44 ms
each (~20 % of the wall time). The diagnostic files cost ~12 ms per 26 apps: batching them would not be noticeable.
The reapply-history store (re-reads up to 200 rows per result) was not exercised: Android kept the updated fixtures
hidden, so nothing was rewritten; its cost appears only in a real reapply (reboot / app-open / manual).

Reapply-history cost, measured on the PC instead (Robolectric, temporary test, not kept): 26 records into a full
200-row file take 30-41 ms. Even at 3-5x on the phone that is ~0.1-0.2 s per 26 reapplied apps (~1-2 % of the wall
time), and only on reapply paths (adding new apps records nothing). Decision input: batching the side records
(plan step 2) would not be noticeable, so it is not worth touching the record code for speed.

## Shared groups with overlapped waits (owner: "진행해줘", 2026-10-18)

`SharedGroupEngine.executeWindow`: up to 8 consecutive groups per helper (as before) are started one after another and
their 500 ms / 1500 ms checks share the wait, like `SafetyEngine.userWindow` does for single apps. Unchanged per group:
validation, durable PENDING record before the setter, preflight read, one UID setter, the 0/500/1500 ms checks, rollback
rules, final commit. A group that does not finish cleanly stops new starts (already written groups still get every
check); broken storage leaves written groups PENDING without rollback (B-1 recovery on app open), as for single apps.
The watch path (`WatchEngine`) still runs groups one at a time. Tests: `SharedGroupWindowTest` (5), all suites pass
(core 368, app 436 + 436, assemble, lint).

Phone (release-signed `artifacts/archive/1.1.4-tests/measure-group-window.apk`, same 26 fixtures, 213 owner records kept):

| Run | Before | After | Groups before -> after |
|---|---|---|---|
| Restore 26 | 9162 ms | 6100 ms | 4909 -> 1861 ms |
| Add 26 | 9284 ms | 5932 ms | 5041 -> 1759 ms |

Home showed 213 after the restore and 239 applied after the add.

Codex review (2026-10-18, `artifacts/archive/reviews-and-reports/1.1.4-group-window-codex-review/`), checked before
fixing: one real defect. When the shared wait is interrupted and the first group's rollback record cannot be saved, the
loop still sent a rollback setter to the next group (the single-app window re-checks `storageFailed` per target; the group
window did not). Fixed by re-checking per group; regression test `interruptedWaitStopsRollbackSettersAfterAFailedSave`
fails on the old code (extra `(test.g1.a, 256)` write) and passes now. Codex's 9 independent probe tests also pass on the
fixed code (run once, not kept). Drift test renamed to say what it checks (isolation, not a real rollback). Documented
trade-off: other groups may already be written when one group's later check fails; they are still fully verified.
All suites pass (core 369, app 436 + 436, assemble, lint).
