## Risks reviewed before the change, and how each is handled

| Risk | Handling | Checked by |
|---|---|---|
| A group's failed record keeps the old `changedByUs`, so a retry rule using it never fires for groups | Retry rule does not use it; needs a write that reached the checks + every member exactly as before the write | `groupResetDuringChecksIsRetriedToo` |
| A failure before any write (also FAILED_SAFE) must not be retried | Retry only when the checks observed a write | `partialSetterFailureExecutesNarrowRollback` (setter error: no retry) |
| Something else changed (other flags, install) | Every app must equal the pre-write read (location-use time aside) and pass `WatchPolicy.skipReason` again | `otherChangeDuringChecksStaysLocked`, `verificationFailureRollsBack...` |
| Endless retry | At most 3 retries, 5 s apart | 4 writes then FAILED_SAFE (single and group tests) |
| A user action waiting behind the retry | `canStart` (watch available, no foreground batch) checked after each wait | code path; wait ≤ 5 s + 1.5 s checks |
| D-2a: a cap could end the 5 s follow-up earlier than 5 s after the latest event | The capped send keeps the names; the window still ends a full delay after the latest event | `eventWindowCapsAStreamWithoutDroppingTheLastCheck` |
| D-2a: a lone event must keep 0.75 s / 5 s | Unchanged path | same test + device (below) |

## Found during device testing

Back-to-back installs of a disposable QA app (12 × `pm install -r`, ~1.3 s apart): Android reset the flag, the watch
re-hid it and the next install landed during the checks (identity changed), so the rollback could not be confirmed:
FAILED_ROLLBACK with no way out in the app. Fixed: `Reconcile` lowers a single-app FAILED_ROLLBACK to FAILED_SAFE
when the same install, owner, firmware and other permission state are in place with the original bit (no write)
(`lockOnAnAppBackAtItsOriginalDropsToCheckNeeded`). The remaining case (Android leaves it hidden) stays locked:
BACKLOG F-1.
