# rc21 후속 보강 — Claude 검수용 인계

## 소유자용 요약

요청한 1·2·4·5·6번을 수정했다. 3번(모두 복원 요청을 먼저 기록하는 저장 방식)은 변경하지 않았다. 작업 기준은 Claude의 `39e1fda` / rc21이며, 이번 변경은 커밋하지 않은 작업 폴더에 있다. 버전 번호·배포 폴더·공개 저장소는 변경하지 않았다.

- 자동 제외 직전에 한 번 더 조회한다. 두 결과가 같을 때만 제외하고, 기존 원래 값·서명·설치 기록은 보존한다.
- 늦은 연결 실패를 정상 감시로 바로잡은 뒤 화면과 위젯도 갱신한다.
- 복원하지 못한 앱은 자동 유지 중인 것처럼 보이지 않게 짧게 안내한다.
- 재시도하지도 않은 뒤쪽 앱의 횟수를 먼저 차감하지 않는다.
- 사용자가 지운 알림은 같은 문제로 반복해서 띄우지 않는다. 새로운 앱의 문제, 해결 후 재발은 다시 알린다.

## 1. 자동 제외 직전 재확인

`core/.../Domain.kt`의 `Reconcile.read`에 선택적 `confirmLocationRemoval` 조회를 추가했다. 기존의 엄격한 자동 제외 후보 조건을 모두 만족하는 경우에만 추가 조회한다. 일반 앱 조회량은 늘리지 않는다.

두 Snapshot의 `invariantEquals`로 설치 식별 정보(버전 포함), 권한 선언/허용, 플래그, 공유 소유자 및 authoritative 여부 등을 비교한다. 위치 사용 시각·표시 이름처럼 제외 판단과 무관한 값은 비교하지 않는다. 콜백 없는 캐시 조회만으로는 제외할 수 없다.

- 결과가 달라지거나 앱이 사라짐: 두 번째 상태를 기존 Reconcile 규칙으로 판정하되 자동 제외하지 않는다.
- 두 번째 조회 예외: 호출 경로가 실패 처리하며, 제외 기록은 저장하지 않는다.
- 기존 제외 기록: 다시 자동 등록하지 않으며 기존 보존 규칙 그대로다.
- 연결 지점: MainActivity의 부분/전체 확인, SetupRuntime의 마지막 확인, WatchEngine, LocalAdbSession의 debug proof. 모두 실제 backend/port.read를 호출한다.

한 번 더 읽는다고 운영체제의 미래 변경까지 원자적으로 막는 것은 아니다. 읽은 두 시점 사이의 불일치를 보수적으로 거르는 보강이다. 권한 setter는 추가하지 않았다.

## 2. 감시 상태 갱신

`WatchClient.lost`의 정상 연결 분기에서 함수 전체를 조기 반환하지 않게 변경했다. 기존 attach용 queueLock 안에서 상태를 정리한 뒤, 잠금 밖의 `LifecycleEvents.changed()`를 양쪽 분기에서 호출한다. 실제 USB 디버깅 OFF는 여전히 감시 중지로 처리한다.

## 4. 복원 미완료 안내

`UiModel`의 enabled + restoreRequested 항목은 완료 집계에서 제외하고 ‘직접 확인할 앱’에 넣는다. 상세와 등록 목록 상태 문구:

> 복원을 완료하지 못했어요. 이 앱의 자동 재적용은 중지했어요.

앱 추가 목록의 짧은 상태는 ‘등록한 앱’으로 표시한다. 기존 package 인덱스를 재사용해 행마다 전체 저널을 다시 검색하지 않는다. 공유 앱·복원 잠금에 대한 별도 안전 안내는 유지한다. 완료된 복원(enabled=false)에는 이 안내가 붙지 않는다. 실제 permission flag가 켜졌다고 주장하지 않는다.

9개 번역을 추가했다. 기존 저장 오류 문구나 enum을 바꾸지 않았다. Terra가 화면/번역/초기 테스트를 맡았고 주 에이전트가 코드와 렌더링을 검수했다.

## 5. 실제 재시도에만 횟수 저장

`WatchClient.signal`에서 allowed 전체를 먼저 차감하던 줄을 제거했다. `WatchEngine.beforeAttempt`에서 해당 처리 단위의 최신 등록·조회·skip 검사 및 취소 확인 후, 기존 hide 엔진에 들어가기 **직전**에 재시도 기록을 저장한다.

- 앞 앱의 실패로 뒤 앱에 도달하지 않음 / 사전 조회 실패 / 건너뜀 / 처리 전 취소: 뒤 앱 횟수 미차감.
- 기록은 작업 결과가 나온 뒤가 아닌 작업 전에 저장하므로, 프로세스 종료로 횟수 기록 자체를 건너뛰지 않는다.
- 실제 시도란 setter 성공 횟수가 아니라 검사를 통과해 재적용 절차에 진입한 횟수다. 저장 직후 강제 종료나 이후 사전 검사의 거절은 보수적으로 한 번 소비할 수 있다.
- SharedPreferences.commit 실패를 이제 확인한다. 실패 시 예외가 hide 진입 전에 처리되므로 permission write하지 않는다.
- 기존 10분 간격/24시간 제한, 한 번의 작업 내부 settling 재확인·롤백, 일반 업데이트 처리 정책은 유지한다.
- 횟수 미차감의 부작용도 보강했다. 이미 시간이 된 재시도가 조회 실패 등으로 실제 처리에 진입하지 못하면 기존 `wait=0 → 최소 30초` 타이머가 계속 반복될 수 있었다. 이 경우 다음 타이머는 10분 뒤로 둔다. 아직 10분 대기 중이면 기존 남은 대기 시간을 사용한다. 새 패키지 이벤트로 인한 정상 조회까지 막는 정책은 아니다.

## 6. 알림을 지운 의도 보존

`LifecycleReceiver.kt`의 기존 non-exported 수신기를 명시적 immutable deleteIntent로 재사용했다. 새 receiver/service/권한/인터넷/타이머를 추가하지 않았다.

`reapply-notices` 앱 내부 preferences에 미해결 문제별 임의 식별자와 지운 식별자를 저장한다. 이는 인증 토큰이 아니며 헬퍼 접근과 무관하다. 설치 식별자가 같고 문제가 계속 미해결이면 실패 상태·시각·버전이 바뀌어도 같은 문제로 취급한다. 해결을 확인하거나 다른 설치로 바뀌면 새로운 식별자를 사용한다.

- A 알림 삭제 → A 재시도 실패: 다시 알리지 않는다.
- A 미해결 중 B에 새 문제: A+B 총 개수의 통합 알림을 표시한다.
- B 해결, 남은 것은 이전에 지운 A뿐: 통합 알림도 없앤다.
- A 해결 확인 후 재발: 다시 알린다. B가 계속 미해결이어도 A의 문제 구분은 새로 시작한다.
- 오래된 알림의 삭제 신호가 뒤늦게 도착해도 신규 문제까지 지우지 않는다.
- 기존 알림 스위치·OS 알림 권한·채널·전경 억제·다른 종류 알림은 유지한다. 지워도 앱 안의 미해결 목록은 그대로 보인다.
- 해결 관찰 경로도 연결했다. 기존에는 MainActivity에서 숨기기 성공일 때만 clear했지만, 이제 BatchPipeline의 결과 처리에서 복원·숨김 풀기도 포함해 정리한다. Activity가 없거나 닫혀도 처리하며, MainActivity/SetupRuntime의 정상 재확인 후에도 미해결 목록과 대조한다. 알림 정리 실패는 runCatching으로 실제 작업 결과를 실패로 뒤집지 않는다.
- 알림 관련 저장 실패 시 해당 동작을 중단한다. 숨김/복원 저널을 수정하지 않는다.

‘삭제’는 알림을 밀어 지우거나 모두 지우기다. 알림을 눌러 앱으로 들어가는 행동은 삭제와 별개다. 앱이 실제로 관찰하지 못한 ‘중간에 해결됐다가 다시 실패한 사건’까지 구별한다고 주장하지 않는다.

API 근거: [Android Notification.Builder.setDeleteIntent](https://developer.android.com/reference/android/app/Notification.Builder#setDeleteIntent(android.app.PendingIntent)) — 사용자가 알림을 명시적으로 지울 때 호출된다. 성공 후 앱이 cancel한 경우와 혼동하지 않는다.

Luna 독립 검토에서 clear 경로의 알림 저장 실패 반환 누락을 확인해 반영했다. 주 에이전트가 추가로 ‘새 B가 해결되면 지워둔 A만 남기지 않기’ 경합을 보강했다.

## 다음 실기기 확인 절차(이번에는 미실행)

1. 잠금 해제·기존 서명 일치 확인 후 업데이트 설치만 한다. 삭제/데이터 초기화하지 않는다.
2. 실패 알림이 자연스럽게 생기거나 승인된 QA 앱으로 재현되면 알림을 밀어 지운다. 동일 앱의 재시도 뒤 다시 뜨지 않고, 홈의 확인 목록은 남는지 확인한다.
3. 다른 QA 앱의 새로운 실패는 통합 알림을 만들고, 그 앱을 해결한 뒤 남은 것이 지운 문제뿐이면 알림이 사라지는지 확인한다.
4. 복원 실패는 승인된 QA 앱/통제된 연결 실패로만 시험한다. 안내 문구, 자동 재적용 제외, 이후 복원 성공 시 안내 해제를 확인한다. 실제 사용자 앱을 임의로 실패시키거나 권한을 빼앗지 않는다.
5. 위치 권한을 선언하지 않는 새 버전 QA 앱을 업데이트해 자동 제외와 기록 보존을 확인한다. 진행 중 다른 업데이트/삭제가 겹치면 자동 제외 대신 확인 대상으로 유지되는지 본다.
