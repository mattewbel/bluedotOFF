# 위젯 시간 초과 뒤 재요청 수정 — Claude 인계

기준 HEAD `bcdde25`, Codex. 사용자 요청: 시간 초과 직후 다시 누를 때 서비스가 남는 문제를 안전하게 수정·시험하고, 기존 앱들의 상태를 유지할 것.

## 수정 내용

`WidgetCheckService.kt`의 수명 처리만 바꿨다.

- `ownsWork`로 이 서비스 인스턴스가 현재 작업을 맡고 있는지 구분한다. 프로세스 공통 `running`이 true여도, 이전 인스턴스의 취소 작업 때문이면 새 서비스는 위젯 진행 표시와 자기 foreground를 정리하고 바로 종료한다.
- 같은 살아 있는 인스턴스의 중복 요청은 기존 작업을 유지한다. 오래된 요청·foreground 시작 실패에도 같은 소유권 기준을 쓴다.
- 취소·종료 중인 인스턴스는 새 작업을 받지 않는다.
- 실제 worker가 끝난 뒤 위젯 완료 표시 → 서비스 종료 → `running` 해제를 메인 스레드에서 연달아 처리한다. 옛 작업이 먼저 `running=false`를 풀고 뒤늦게 새 작업의 표시·서비스를 지울 수 있던 경합을 막는다.
- 시간 초과 시 `running`을 미리 false로 풀지 않는다. 연결 정리를 마치지 않은 옛 작업과 새 작업이 겹치지 않아야 하기 때문이다.

`StatusWidget`, `WirelessWork`, 연결 종료 안전 정책, Binder/helper 권한 변경, 숨김·복원 엔진, 저널 저장 형식/방식은 변경하지 않았다. 새 UI 문구·번역·권한·서비스·라이브러리·버전 변경도 없다.

## 회귀 시험

`WidgetCheckLifecycleTest`에 실제 재현 상황을 포함한 5개 시험을 추가했다.

1. 시간 초과 뒤 옛 worker가 잠금 대기 중일 때 새 서비스가 즉시 종료하는지. 같은 정상 인스턴스의 중복 시작은 유지되는지도 함께 확인한다.
2. 오래된 요청으로 생성된 새 서비스도 종료하고, 옛 worker의 잠금을 풀지 않는지.
3. 정상 작업 중 오래된 중복 요청이 와도 기존 서비스를 멈추지 않는지.
4. worker가 끝나도 메인 스레드 정리 전에는 공통 잠금을 유지하고, 종료 중인 옛 인스턴스가 다시 작업을 받지 않는지.
5. 정리가 끝나면 다음 서비스 인스턴스는 새 요청을 받을 수 있는지.

기존 `WidgetCheckWaitTest`의 정리 단계에는 worker 종료 뒤 메인 큐를 비우는 한 줄만 추가했다. 기대 결과를 완화하지 않았다.

관련 29개 시험 통과: 신규 수명 시험 5 + 대기/취소 4 + 서비스/정리 안내 6 + 위젯 14. 수정 전 실패 XML과 실기기 재현 증거는 `research/device-widget-idle-20261106/`에 보존했다.

## 결정한 경계

종료를 시작한 같은 인스턴스에 아주 늦게 전달된 요청은 버린다. 새 요청을 뒤늦게 자동 실행하거나 취소된 작업과 겹치게 하지 않는 기존 정책을 따른 것이다. 정상 종료 뒤 새 인스턴스의 요청은 다시 받는다.

### Fold7 실제 시간 초과·재요청

실제 서비스 소스를 재사용한 격리 QA 패키지 `app.bluedotoff.widgettimeoutqa`로 시험했다. 기존 앱과 데이터가 분리되며 INTERNET / ACCESS_LOCAL_NETWORK / WRITE_SECURE_SETTINGS 권한을 제거했다. 페어링·키는 가짜 fixture이며 실제 사용자 키를 복사하지 않았다. 연결 잠금을 210초 잡아 실제 Android shortService 시간 제한을 넘겼다. 테스트 코드에서 `onTimeout()`을 직접 호출하지 않았다.

- 181.00초에 첫 서비스가 종료됨. 186.19초에 실제 재요청을 보냄.
- 191.46초, 196.62초 이후에도 새 서비스가 남지 않았고 위젯 진행 표시가 꺼져 있었다. 수정 전 같은 조건에서는 새 서비스가 232초 뒤에도 foreground로 남았다.
- cached process 동결 후 QA 빈 Activity로 실행만 재개하자, 227.70초와 232.86초에 옛 worker 종료와 잠금 해제가 확인됐다(`blocked=false`, `running=false`, `refreshing=false`, `lockReleased=true`). 새 확인을 요청해 취소를 우회하지 않았다.
- 저장된 46개 관측에서 무선 디버깅은 모두 OFF, 확인 시각은 최초 fixture 값 그대로다. `fix/observed-assertions.json`의 5개 관측 검증 모두 통과했다.
- **232.86초 관측 뒤 USB 연결이 사라져 자동 스크립트가 중단됐다.** 사용자 재연결 후 아래 별도 정리·비교를 완료했다. 원래 스크립트가 처음부터 끝까지 성공한 것으로 기록하지 않는다.

### 재연결 후 정리·기존 앱 보존 확인 완료

사용자 재연결·잠금 해제 뒤 `finish_fixed_timeout.py`를 실행했다. 실제 설치 hash가 이번 QA APK와 같은지 확인한 뒤 **격리 QA만 삭제**했고, 패키지가 사라진 것을 재확인했다.

- 위치 권한·표시 플래그 206개 항목의 전후 digest가 `db9fb1da…f5e4a9`로 일치, 차이 0개. 원래 앱은 수동 적용·복원하지 않았다.
- 원래 bluedotOFF APK `95982bda…acc6f1`, 최초 설치·마지막 업데이트 시각 모두 이전과 동일. 수정 APK를 원래 앱에 덮어 설치하지 않았다.
- 실제 bluedotOFF의 확인 서비스와 활성 알림이 남아 있지 않음. QA 패키지와 이번 시험의 UI dump 임시 파일 삭제 완료.
- 강제 Doze 해제 상태, 배터리 모의 상태 없음, 절전 설정 OFF. 무선 디버깅 OFF / USB 디버깅 ON / 모바일 데이터 ON.
- **Wi-Fi는 시험 전 ON, 재연결 후 OFF였다.** 엄격한 전후 비교가 이 차이를 실제로 검출하여 스크립트의 마지막 assertion은 실패했다. 이 fixed-QA 실행은 무선 설정 쓰기를 하지 않고, QA에도 해당 권한이 없다. 연결이 끊긴 동안 누가/무엇이 바꿨는지는 확인하지 못했다. 사용자의 현재 OFF 상태를 임의로 ON으로 되돌리지 않았다. 따라서 '모든 시스템 설정 전후 동일'이라고 주장하지 않는다.

재연결 후 저장된 `fix/cleanup-verification.json`의 항목을 별도로 확인하여 QA 정리, 원래 APK·위치 권한 보존, 디버깅/데이터 설정 유지, 강제 절전 해제를 검증했다. 서비스 생성/종료 event log는 재연결 시 남아 있지 않아 추가 근거로 사용하지 않았다. 실제 시간별 관측은 앞서 저장한 `system-samples.json`을 근거로 한다.

실제 통신 중 영구 정지한 socket, 자연 방치 장시간 절전, production 앱을 교체한 뒤의 실기기 시험은 이번 수정에서 하지 않았다. 연결 후 취소·안내 보존·기존 동작은 전체 회귀 시험으로 검증했다. Luna의 제한된 읽기 전용 수명/동시 실행 검토도 메인이 코드와 대조했으며, Claude의 이번 수정 검수는 아직 받지 않았다.

## 변경·배포 범위

- 개발 작업 폴더의 수정·전체 검증 완료. 커밋·push·공개 저장소·업로드 폴더 변경 없음.
- 기존 폰의 실제 bluedotOFF를 교체하거나 열어 자동 재적용을 유발하지 않았다. 별도 패키지의 동일 서비스 코드로 실제 Android 3분 제한을 검증했다.
- 원래 앱의 적용/복원 버튼, 설정 스위치, 데이터 초기화는 사용하지 않았다. 시험 전후 위치 권한·플래그 동일을 확인했고 시험 앱 정리를 완료했다. Wi-Fi의 별도 변화는 위와 같이 공개하고 현재 OFF를 유지했다.
