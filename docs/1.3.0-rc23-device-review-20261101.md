# rc23 실기기 검수와 보완 (Codex, 2026-11-01)

## 요약

클로드의 rc23(`b655266`, 검증 기록 `9218c91`)을 검수했다. 기존 213개를 모두 복원하지 않고 별도 패키지로 기능을 시험했다. 실제 갤럭시에서 두 디버깅을 끌 수 있었고, 초기 PC 선택의 뒤로가기도 동작했다. **프로세스 복원 뒤 PC 선택 유실**, **배포 감사 스크립트 불일치**, **읽을 수 없는 복원 기록을 0개로 오인한 삭제 승인** 세 가지를 찾아 보완했다.

## 발견한 문제와 수정

1. **PC 선택 직후 프로세스 종료 → 화면 복원 → 뒤로가기가 Wi-Fi 대신 화면 종료**
   - `LocalAdbSetupActivity`는 화면에서 새로 PC를 골랐다는 `PC_CHOSEN_HERE`를 로컬 Intent에만 기록했다. Android가 새 프로세스에서 작업을 복원할 때 이 로컬 변경이 사라졌다.
   - QA 실제 프로세스 PID가 바뀐 뒤 같은 작업 화면을 복원해 Back을 눌렀을 때 Wi-Fi 단계로 가지 않고 화면이 닫혔다. 새 자동 재현 시험도 `Back must return to Wi-Fi after process restoration`에서 실패했다.
   - `onSaveInstanceState`에 boolean을 저장하고 `onCreate`에서 복원하는 두 지점만 보완했다. 기존 PC 사용자에게 없는 표식은 새로 만들지 않는다. 수정 후 같은 실제 프로세스 종료/작업 복원에서 Wi-Fi 4단계 복귀를 확인했다.
2. **`scripts/finalize.py`가 rc23 배포 준비를 차단**
   - 이전 `Settings.Global.putInt` 호출 수 2개 검사와 달리, 새 `disableDebugging()`까지 실제 3개라 기존 assert가 실패한다.
   - 3개를 검사하되 새 쓰기는 권한 확인 뒤 `adb_wifi_enabled` 및 `ADB_ENABLED` 두 고정 키에 OFF(0)만 쓰는지 추가로 확인한다. 임의 키, ON 값, 권한 검사 누락, 추가 쓰기를 넣은 4가지 변형이 모두 거부되는 자체 시험을 통과했다.
3. **복원 기록 오류인데 빈 화면을 0개로 간주해 디버깅 OFF/삭제 승인**
   - `beforeUninstall`은 journalProblem이나 실제 기록 읽기를 확인하지 않고 화면의 entries가 비어 있으면 ‘모두 복원’ 정리를 수행했다. CRC 오류를 넣은 새 시험과 known journalProblem 시험에서 USB가 실제로 0으로 바뀌어 실패했다. 설정 화면도 0개 경고와 시작 버튼을 내보냈다.
   - 알려진 기록 오류는 실행을 차단하고, 실행 직전에 `store.entries()`로 체크섬 검증을 거친 실제 기록을 읽는다. 읽기 실패는 journalProblem으로 전환하고 삭제 승인을 지운다. 성공한 경우만 그 실제 목록으로 처리한다. 기록 파일을 쓰거나 복구하는 코드는 추가하지 않았다.
   - Settings 경고도 오류가 있으면 기존 번역의 ‘복원 기록을 확인하지 못했어요’와 ‘앱을 삭제하지 마세요’ 안내만 보여 주며, 시작 버튼을 제공하지 않는다. 9개 언어 모두 기존 키가 있다.
   - 실제 QA 내부 파일만 읽을 수 없게 한 후 빈 화면 상태의 실제 beforeUninstall을 호출했다. `journalProblem=true / uninstallCheck=null / usb=1 / wireless=0`으로 차단된 것을 확인했다. 정상 빈 기록으로 되돌린 QA에서는 기존 5초 경고와 정리가 다시 통과했다.

## 실제 폰에서 확인한 것

- 원본 앱: 213개 복원 경고와 카운트다운을 보고 **취소**. 전체 복원은 실행하지 않았다.
- 독립 QA: 등록 0개여도 경고가 뜸, 5초 전 버튼이 비활성이고 실제 조기 탭도 실행되지 않음.
- 권한 없는 QA: 실제 `MainActivity.beforeUninstall()`의 0개 경로 실행 후 개발자 옵션에서 직접 끄라는 완료 안내. USB ON / 무선 OFF 유지.
- 권한 있는 QA: 같은 삭제 전 정리 경로가 무선 ON→OFF, USB ON→OFF로 변경. QA 일반 앱 UID에 WRITE_SECURE_SETTINGS를 준 시험이며 root/SELinux 변경 없음. 실제 PC ADB 연결도 끊겼다.
- QA가 두 값 0을 관찰하고 1.5초 후에도 둘 다 0임을 파일에 남김. 별도 복구 스레드가 최초 값으로 돌려 약 9.3초 후 PC 연결 복귀. 기존 원본 helper는 실제 USB OFF로 종료되어, 같은 서명/설치 경로의 PC 시작 명령으로 다시 연결했다.
- QA 초기 설정 4단계에서 PC 선택 → 일반 Back → Wi-Fi로 복귀.
- QA에서 Activity.recreate 후 같은 Back → Wi-Fi로 복귀.
- QA 프로세스만 `am kill`하고 기존 작업을 새 프로세스에 복원 → 기존 rc23은 실패, 수정본은 Wi-Fi 복귀.
- 기존부터 PC 방식인 QA 화면은 Back으로 종료되고 PC 선택은 유지됨. 수정 전후 확인.
- QA는 별도 패키지 `app.bluedotoff.rc23qa`. 원본과 journal/prefs/helper를 공유하지 않는다. 설치 화면 시험은 실제 컨트롤러/세션을 사용했다. 0개 복원 시험만 QA 시작 도우미가 MainActivity의 화면 모델을 Settings/READY로 열어 줬으며, 실제 정리 함수·Settings provider는 대체하지 않았다.
- QA 앱은 삭제했고 Wi-Fi ON / 무선 OFF / USB ON / 모바일 ON으로 복구. 원본 홈 213개 적용/등록 및 원본 감시 연결, 활성 4201 없음 확인. 위치 권한 허용/거부나 213개 전체 복원은 하지 않았다.

## 추가 자동 시험

- `SetupScreenTest.backOnPcChosenHereSurvivesProcessStateRestoration`: 원본 launch Intent + 저장 Bundle로 재생성해 새 선택의 Back 동작 확인. 기기 시험과 별도로 복원 상태 유실을 재현한다.
- 새 `UninstallDebuggingTest` 5개 중 3개: 원래 연결을 켜 둔 상태에서 Activity의 실제 정리 호출부를 통해 복원 미완료(allBack=false), 복원 완료, 인증 만료 원래 값 복구 보류 때의 디버깅 값/화면 완료 여부를 확인.
- 같은 테스트 클래스에 기록 읽기 실패/knownProblem 두 경우를 추가했고, `UiRenderTest.restoreBeforeUninstallBlocksKnownJournalProblems`는 오류 때 시작 버튼 부재와 안내를 검증한다. 세 경우 모두 수정 전 실제 실패, 수정 후 통과했다.
- Luna는 설정 화면/번역 및 위 작은 수정만 읽기 전용 검토했다. 9개 언어의 새 키/숫자 치환/자동·수동 안내 의미에 어긋남을 찾지 못했다. 보안·기기 제어·수정·최종 검증은 메인이 수행했다.

## 검증/설치 결과

- 최종 전체 명령 성공(7분 47초): core 402 + app debug 606 + release 606 = **1,614개**, 실패/오류/건너뜀 모두 0. debug/release APK 빌드 성공, 린트 각각 오류 0 / 경고 109(기존 rc23과 동일). 최종 로그 `research/device-rc23-20261101/full-validation-verified.log`.

## 클로드 인계

- 시작 기준은 `9218c91`이며 이번 변경은 **아직 커밋하지 않았다**. 새 코드/시험/README/CHANGELOG와 이 문서를 함께 검수할 것. 버전 변경, GitHub push, 공개 미러 또는 업로드 폴더 갱신은 하지 않았다. 업로드 폴더의 기존 rc23 파일을 이번 검수 수정본으로 오인하면 안 된다.
- 변경 지점: `MainActivity.beforeUninstall`, `BlueDotUi.SettingsScreen`의 삭제 전 경고, `LocalAdbSetupActivity.onCreate/onSaveInstanceState`, `scripts/finalize.py`. 새 시험 `UninstallDebuggingTest`, `SetupScreenTest` 1개, `UiRenderTest` 1개(총 7개 × 두 app variant).
- 원래 저널 형식·저장/복원 엔진·helper 보안·FINE 0x100 setter는 그대로다. 정식 APK에는 QA용 복구 스레드/driver/설정값 주입 코드가 없다.
- 최종 APK는 `app/build/outputs/apk/local/release/app-local-release.apk`. 이후 소스를 바꾸면 위 해시/기기 일치와 검사 결과를 새 파일에 재사용하지 말 것.

## 범위와 한계

- QA는 실제 Fold7의 일반 앱 권한으로 실행했지만 별도 debug 패키지다. 213개를 실제로 모두 복원한 뒤 감시/자동 관리 종료까지 끝내는 원본 앱 대량 시나리오는 수행하지 않았다. 개별 적용·복원 엔진은 이번 변경 대상이 아니다.
- `qa-radio-off-result.png`는 완료 안내 문구 확인용이다. 촬영 전에 시험 복구 장치가 USB를 다시 켰으므로, 이 이미지 자체가 촬영 당시 USB OFF 증거인 것은 아니다. 실제 OFF 증거는 `radio-proof.jsonl`의 두 0 값과 PC ADB 연결 단절이다.
- 최초 QA 준비 중 보조 Kotlin 클래스 누락으로 QA만 한 번 종료됐다. 시험 빌드를 고쳐 실제 dex 포함을 확인한 뒤 진행했으며, 원본 앱의 오류가 아니다.
- 배포용 산출물 덮어쓰기를 피하기 위해 감사 스크립트 전체 실행은 출력 위치만 `research/device-rc23-20261101/audit-scratch`로 돌리는 시험 도구를 사용한다. 배포 artifacts/공개 저장소/업로드 폴더는 변경하지 않는다.
- 근거: `research/device-rc23-20261101/`의 before/after 프로세스 복원 JSON, 실제 화면, radio-proof, targeted/full 검사 로그. 앱 삭제·데이터 초기화는 QA 패키지에만 했으며 원본 데이터는 보존했다. 커밋/푸시하지 않았다.

- 기준 `8b281ce`. 소유자가 안전한 부분만 수정을 요청했다. 1번의 중복 버튼만 정리했다. 기록 오류 창은 ‘확인’만 표시하며, 정상 창의 ‘취소’와 5초 대기는 유지한다. 새 문구나 번역 키는 추가하지 않았다.
